# RTK-preferred startup evidence

The initial ten behavioral cases were written before the navigation implementation changed. Baseline 50bd771 navigation failed eight for the intended reasons and passed the stale/future and no-GNSS preservation cases (`startup_quality_red.log`). The final suite adds four deadline/ordering/reset preservation cases and passes 14/14 (`startup_quality_green.log`). The complete portable Release CTest suite passes 17/17 (`startup_quality_ctest.log`). Source hashes and commands are in `startup_quality.json`.

Status=2 has its own sample and timestamp history for each antenna. Lower-quality timestamps cannot suppress RTK, lower-quality samples cannot bias its median, and RTK heading uses RTK from both antennas with the existing pairing geometry/time/coherence gates. A full RTK master window anchors immediately; a full RTK rover window can anchor after the existing 1.5-second rover delay when no RTK master has arrived. The unchanged five-second deadline allows sparse RTK or usable status0/1 fallback. With no GNSS, relative output resumes after the same deadline. Reset clears both quality groups.

Expected coverage change: a run starting with lower-quality GNSS now holds position until sufficient RTK arrives or until the deadline. Velocity continues during the hold. No existing test fixtures needed changing: immediate-anchor navigation fixtures already specify status=2. No public-reference result was used to choose parameters or behavior; evaluate public coverage and errors only after the source freeze. Continuous GNSS correction behavior and geometry are unchanged.
