# Атлас датасета трамвайной телеметрии

Это read-only исследование распакованных `dataset/data/*/*.db3`. Исходные bag не
изменялись. Описание официального контракта и ограничений находится в
[`dataset/README.md`](../dataset/README.md); в частности, GNSS разрешён для
анализа, метрик и начальной выставки, но не как постоянный вход оценивателя.

## С чего начать

Для покадрового 3D-повтора всех bag с перемоткой и подсветкой аномалий
запустите [`simulator/`](simulator/README.md).

1. Откройте [`viewer/dataset_explorer.html`](viewer/dataset_explorer.html) в
   обычном браузере. Это автономный файл: все 122 прогона, скорости двух
   тележек, ручка, GNSS-скорости и траектория. Интернет и ROS не нужны.
   Начальный прогон `30618_0e41eac3` — относительно чистый пример. Выберите
   другой bag в списке; мышью можно увеличивать график и скрывать каналы.
2. Откройте [`routes/map_explorer.html`](routes/map_explorer.html), чтобы
   сравнивать маршруты, направления и качество GNSS на всей выборке.
3. Для точных локальных эпизодов смотрите PNG в [`signals/`](signals/) или
   постройте полный график одного bag:

   ```powershell
   py -3.12 analysis/viewer/make_plots.py 30618_33bec73f 30639_3b3d9eb8
   ```

   Выходы появятся в `analysis/viewer/figures/`. Нужны NumPy, Matplotlib и
   pyproj. Скрипт читает SQLite/CDR напрямую, не требует ROS. Подписанный на
   PNG RMSE — **сырой диагностический** показатель относительно выбранного
   GNSS, без полного отбраковывания плохого эталона; не используйте его как
   турнирную метрику.

## Устройство набора

| Свойство | Фактически |
| --- | ---: |
| Bag | 122: `30618` — 103, `30639` — 19 |
| Уникальные SQLite-записи | 97; есть 25 пар точных дублей |
| Длительность | 36,746 ч суммарно; медиана 19,85 мин |
| Сообщения | 8 788 325 |
| Размер SQLite | 863 756 288 байт, ≈823,7 MiB |
| Без GNSS-сообщений | 35 bag, хотя четыре GNSS-топика объявлены в метаданных |
| Только rover GNSS | `30639_e4379d7f` |

В каждом каталоге есть `metadata.yaml` и один `*_0.db3`. Метаданные содержат
семь объявленных топиков; реальное число сообщений смотрите в
[`catalog/topics.csv`](catalog/topics.csv) или через `ros2 bag info`.

| Топик | Тип | Частота, примерно | Роль |
| --- | --- | ---: | --- |
| `/vehicle/driver_position_cmd` | `tram_vehicle_msgs/msg/DriverControllerCommand` | 20 Гц | Вход: целое −15…15 |
| `/vehicle/front_bogie_velocity` | `tram_vehicle_msgs/msg/VelocitySensor` | 10 Гц | Вход: передняя тележка |
| `/vehicle/rear_bogie_velocity` | тот же | 10 Гц | Вход: задняя тележка |
| `/sensing/gnss/{master,rover}/fix` | `sensor_msgs/msg/NavSatFix` | 10 Гц | Эталон положения и начальная выставка |
| `/sensing/gnss/{master,rover}/vel` | `geometry_msgs/msg/TwistStamped` | 10 Гц | Эталон скорости |

**Критическая ошибка единиц в исходном описании:** поле `VelocitySensor.velocity`
названо скоростью в м/с, но численные данные bag соответствуют **км/ч**.
Сравнение с GNSS подтверждает масштаб: для м/с используйте `raw / 3.6`.
Это вывод из датасета, а не изменение `.msg`-схемы. Максимум сырых показаний
≈54; после пересчёта это ≈15 м/с и согласуется с GNSS.
Проверка на чистом `30618_0e41eac3` даёт наклон `raw/GNSS = 3,5989` и
RMSE `raw / 3.6` 0,036 м/с против 19,064 м/с при ошибочной трактовке raw
как м/с. На `30639_584b6e32` наклон 3,5876 и RMSE 0,041 м/с после
пересчёта. Метод воспроизводится скриптом
[`viewer/verify_units.py`](viewer/verify_units.py).

Локальные графики по первым, вторым, третьим, общему юзу и ложным тревогам:
[`signals/`](signals/). При разработке детектора нужно различать истинное
скольжение, пропуск датчика, задержку сообщений и неисправный GNSS-эталон.

Отдельная калибровочная разведка [`signals/NOTCH_README.md`](signals/NOTCH_README.md)
показывает зависимость ускорения от позиции ручки **и скорости** для каждого
трамвая. Позиция `−15` чаще удерживается уже возле остановки (около 80% её
отфильтрованных отсчётов при <1 м/с), поэтому её простое среднее ускорение
кажется почти нулевым. Есть и эпизоды, когда при непрерывной `−15` обе
тележки и оба GNSS согласованно показывают разгон; по доступным сигналам
причину установить нельзя. Для модели это повод калибровать по скорости,
фазе команды и трамваю, а сомнительным режимам давать широкую неопределённость.

## Геометрия маршрута и качество эталона

- В 86 bag есть master position, ещё в одном — только rover. Полных проходов
  общего маршрута с master — 73: 38 в одну сторону и 35 в обратную.
  Длина полного пути около **5,3–5,5 км**. Встречные пути на общем участке
  разделены медианно на **3,79 м**, поэтому карта должна учитывать направление.
- Master и rover расположены в разных местах трамвая: медианное продольное
  разделение около **12,44 м**, rover впереди по ходу движения. Не нужно
  усреднять их позиции как одну точку `base_link`.
- У всех `NavSatFix` тип ковариации `UNKNOWN`, матрица ковариации заполнена
  нулями. Среди соседних master fix **4 159 / 926 876** шагов дают кажущуюся
  скорость >30 м/с, включая сообщения со status 2. Производная сырой позиции
  и сумма её шагов не подходят как чистый эталон скорости и длины пути.
- Сравнение колёс с GNSS-скоростью на уникальных bag, когда master и rover
  согласуются с точностью 0,3 м/с и оба <25 м/с, даёт для простого среднего
  тележек RMSE **0,0568 м/с** по 607 677 парам `30618` и **0,0817 м/с** по
  176 741 парам `30639`. Это диагностический baseline на очищенном
  подмножестве, **не честная оценка будущего онлайн-решения**: фильтр на основе
  GNSS выбрасывает сложные моменты и не может работать в контуре.
- Использованная в графиках ENU-система имеет выбранную аналитиками точку
  отсчёта. `dataset/README.md` требует метрическое `x/y/z`, согласованное
  с судьёй, но его точка отсчёта и целевая антенна явно не заданы. Для
  будущего решения это отдельный интеграционный вопрос. Два просмотрщика
  используют разные аналитические ENU-начала: общий — `(55.805°, 37.425°,
  170 м)`, карта — первый fix `30618_01f73500`; численные координаты между
  ними нельзя сравнивать без преобразования, геометрия маршрута одинакова.
- Оба колёсных канала дают почти всегда неотрицательную продольную величину;
  редкие отрицательные значения малы и похожи на шум около остановки.
  Направление движения по карте и абсолютную начальную точку по трём
  скалярным входам определить нельзя: их нужно задать внешним состоянием,
  картой/сценарием или GNSS во время разрешённой начальной выставки.

Детали: [`routes/README.md`](routes/README.md),
[`catalog/README.md`](catalog/README.md).

## Время, дубли и проверка модели

- Используйте `header.stamp` для событий, но проверяйте его: медианная задержка
  записи относительно stamp ≈1 мс у команды, ≈50 мс у колёс и ≈45–90 мс у
  GNSS. В семи bag есть обратные скачки stamp; в отдельных — лаг в секунды.
  Сопоставление только по времени записи SQLite создаёт ложные аномалии.
- Разделяйте train/validation/test по группам SHA-256 из
  [`catalog/duplicate_groups.json`](catalog/duplicate_groups.json). Иначе
  точные копии одного прогона окажутся и в обучении, и в оценке.
- Для честной проверки симулируйте исчезновение GNSS после первых секунд,
  не подавайте дальнейший GNSS в фильтр и публикуйте результаты по мере
  поступления входов. Отдельно считайте ошибки на перечисленных эпизодах,
  длительных пропусках и на втором трамвае.

## Просмотр через ROS 2 Humble

ROS 2 в текущем Windows-окружении не установлен; команды ниже предназначены
для Linux с ROS 2 Humble. Автономные HTML и PNG выше уже построены и проверены
без него.

```bash
source /opt/ros/humble/setup.bash
mkdir -p ~/tram_ws/src
cp -r dataset/tram_vehicle_msgs ~/tram_ws/src/
cd ~/tram_ws
colcon build --packages-select tram_vehicle_msgs
source install/setup.bash
ros2 bag info /path/to/mos_transportr_hack/dataset/data/30618_0e41eac3
ros2 bag play /path/to/mos_transportr_hack/dataset/data/30618_0e41eac3 --clock
```

Во втором терминале с тем же `source install/setup.bash`:

```bash
ros2 topic hz /vehicle/front_bogie_velocity
ros2 topic echo /vehicle/driver_position_cmd
ros2 run rqt_plot rqt_plot
```

В `rqt_plot` добавьте `/vehicle/front_bogie_velocity/velocity` и
`/vehicle/rear_bogie_velocity/velocity`; на этих сырых графиках единицы будут
фактически км/ч. Для нескольких потоков, преобразования `/3.6` и поиска
короткого буксования удобнее PlotJuggler, если он уже установлен. RViz2
полезен для готового `nav_msgs/Odometry` и карты, но сырые `NavSatFix` и три
скаляра сами по себе не дают готовую трассу в локальной метрической системе.

## Воспроизводимость

- [`catalog/catalog_bags.py`](catalog/catalog_bags.py) строит полный каталог
  с SQLite и стандартной библиотекой Python.
- [`viewer/rosbag_cdr.py`](viewer/rosbag_cdr.py) — минимальный CDR-декодер
  типов именно этого датасета; он не заменяет универсальную ROS-библиотеку.
- [`viewer/verify_units.py`](viewer/verify_units.py) проверяет масштаб двух
  колёсных каналов относительно согласованных GNSS-скоростей.
- [`viewer/build_explorer.py`](viewer/build_explorer.py) пересобирает общий
  автономный HTML (нужны NumPy, pyproj, Plotly). Обзорные линии прорежены до
  примерно 1 200 точек на сигнал с сохранением локальных минимумов и
  максимумов и явных пропусков. Для точной диагностики используйте PNG/CSV.
- [`routes/README.md`](routes/README.md) перечисляет скрипты GNSS-аудита;
  [`signals/final_metrics.py`](signals/final_metrics.py) фиксирует методику
  очищенного baseline.
