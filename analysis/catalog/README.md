# Каталог датасета ROS 2 bag

Воспроизводимый read-only проход по всем распакованным `dataset/data/*/*.db3`.
Запуск без ROS и внешних библиотек:

```powershell
python analysis\catalog\catalog_bags.py
```

Скрипт открывает SQLite через `mode=ro&immutable=1`, читает все сообщения по времени
записи, разбирает общий `std_msgs/Header` и нужные скалярные поля CDR. Ничего в
`dataset` не пишет. Время выполнения в текущем окружении около минуты.

## Что создано

| Файл | Содержание |
| --- | --- |
| `bags.csv` | Одна строка на bag: размер, длительность, UTC-старт, число сообщений, GNSS, наибольшие разрывы входов, SHA-256. |
| `topics.csv` | Одна строка на bag и топик: counts, интервалы, `header.stamp`, лаг относительно времени записи, значения. |
| `gaps.csv` | Время и длина крупных пропусков: входные скорости >0,5 с, команда >0,2 с, GNSS >1 с. |
| `timing_anomalies.csv` | Старый `header.stamp` (>0,5 с), метка из будущего (>0,1 с), неположительное приращение времени заголовка. |
| `duplicate_groups.json` | Группы побайтно одинаковых `.db3`. |
| `summary.json` | Машиночитаемая общая сводка. |

## Общая структура

- 122 каталога, 122 `.db3` и 7 объявленных топиков в каждом. Фактическое наличие сообщений отличается от списка топиков.
- 8 788 325 сообщений; 863 756 288 байт SQLite (823,7 MiB); суммарная длительность 36,746 ч.
- Длительность bag: минимум 1,282 с, медиана 1190,769 с, максимум 1897,484 с.
- Трамвай `30618`: 103 bag, 30,840 ч; `30639`: 19 bag, 5,906 ч.
- Время начала записей лежит от 2026-05-05 до 2026-09-03 UTC.
- Показатели `metadata.yaml` (start/duration/message_count) совпали с SQLite у всех 122 bag.

## Дубли и разделение выборки

Есть **25 пар побайтно одинаковых SQLite bag**; все пары относятся к `30618`.
Уникальных bag — **97**. Среди дублированных пар 9 с GNSS и 16 без GNSS.
После удаления дублей: 78 прогона `30618`, 19 прогонов `30639`;
78 уникальных прогонов с GNSS, 19 без GNSS.

Поэтому train/validation/test надо делить **по SHA-256-группе**, а не по имени
каталога. Разные имена при одинаковой записи создадут утечку в метриках.

## Покрытие GNSS

- У **35 bag** все четыре GNSS-топика объявлены, но пусты; все они от `30618`.
- У `30639_e4379d7f` master fix и master velocity пусты, rover заполнен.
- В остальных **87 bag** есть хотя бы один GNSS-поток. Первый master fix приходит
  в пределах 0,024 с от начала bag, первый rover fix — 0,020 с.
- Если master fix есть, его последнее сообщение обычно в пределах 0,045 с от
  конца bag (максимум 0,084 с). Это значит, что имеющиеся GNSS-треки в целом
  охватывают весь прогон, а не только первые секунды. Внутри есть разрывы.
- Наибольший разрыв master velocity — **33,372 с** в идентичных
  `30618_4d487b0d` / `30618_b3042f78`; master fix — 29,389 с в тех же bag.

GNSS-скорость тоже требует проверки выбросов при оценке точности: типичный
99-й процентиль внутри bag близок к 14–15 м/с, но одиночные максимумы
достигают 43,835 м/с (master) и 43,773 м/с (rover).

## Входные пропуски и значения

- Наибольший разрыв задней тележки — **73,500 с** в `30639_3b3d9eb8`,
  также там есть разрыв 30,400 с. В `30639_4285f2bc` — 47,099 с.
- Наибольший разрыв передней тележки — **19,801 с** в `30639_c31df386`.
- Разрывы свыше 5 с: передняя тележка 1, задняя 10; все относятся к `30639`.
- Две пары дублированных bag `30618` имеют совместный пропуск обоих колёс и
  команды примерно на 1,0–1,2 с; точные времена указаны в `gaps.csv`.
- Отрицательных показаний колёс мало: 15 передних и 13 задних, до −0,378 и
  −0,389 соответственно. Часть приходится на точные дубли.
- Максимумы сырых значений колёс: 53,730 и 53,920. Это согласуется с
  гипотезой, что численно данные записаны в км/ч, несмотря на описание поля
  как м/с. Масштаб требуется отдельно проверить регрессией на GNSS-скорости.

## `header.stamp` и время записи bag

`header.stamp` — время источника внутри CDR; SQLite `messages.timestamp` — время
записи в bag. Они **не равны**. Медианный лаг `bag − header` по bag обычно:

| Топик | Типичная медиана лага |
| --- | ---: |
| Команда | 0,001 с |
| Передняя / задняя тележка | 0,050 с |
| GNSS master fix | 0,045 с |
| GNSS master velocity | 0,085 с |
| GNSS rover fix / velocity | 0,081 / 0,089 с |

Есть крупные отклонения: до 6,247 с у скорости колёс и 5,506 с у rover fix.
В семи bag обнаружены неположительные шаги времени заголовков (часто скачок
около −1 с). В `30639_3b3d9eb8` около 2,47 тыс. GNSS-сообщений *на каждом*
топике имеют `header.stamp` примерно на 0,95 с **позже** времени записи bag,
тогда как колёсные заголовки обычно близки к записи. В
`30618_40ffd323` и его дубле `30618_efb92709` есть смешанные будущие и
запаздывающие метки времени во всех потоках.

Практический вывод: для расчёта `dt` нужна защита от возвратов, слишком старых
меток и резких скачков времени. При сопоставлении результатов с эталоном нельзя
слепо считать, что ближайшие bag-времена имеют близкие `header.stamp`.

## Границы этого каталога

Интервалы вычислены по **времени записи SQLite**. Скрипт также сравнивает
отдельный `header.stamp`, но не делает семантической синхронизации между топиками.
Поле `NavSatFix.latitude` используется лишь для проверки декодирования CDR;
географическая траектория здесь не строится. Численные минимумы/максимумы не
считаются очищенным эталоном — они показывают сырые данные.
