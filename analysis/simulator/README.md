# 3D-проигрыватель телеметрии трамвая

Это интерактивное **воспроизведение записанных rosbag**, а не физический
симулятор реакции трамвая на произвольную команду. Оно показывает входы,
выход production C++-оценивателя и независимые GNSS-каналы по одной шкале
времени, чтобы покадрово разбирать сбои.

## Запуск

В Windows из корня проекта:

```powershell
py -3.12 analysis/simulator/serve_simulator.py
```

Откройте **http://127.0.0.1:8999/**. Сервер слушает только localhost, читает
`dataset/data/*/*.db3` без изменения данных и работает без ROS 2 и интернета.
Требуются Python 3.10+, `g++` с C++17 и браузер с WebGL. При занятости порта
можно указать `--port 9000` и открыть этот порт. На Linux команда запуска —
`python3 analysis/simulator/serve_simulator.py`. Для заранее собранного
исполняемого файла допустим `--replay-cli /path/to/replay_cli`; иначе сервер
один раз собирает текущие `estimator.cpp` и `evaluation/replay_cli.cpp`.
Временный исполняемый файл в каталоге просмотрщика удаляется при штатной
остановке сервера. Если `g++` недоступен, просмотр сырых данных продолжает
работать, а слой C++ сообщает об ошибке сборки.

## Что можно делать

- Выбрать любой из **122 bag**; полный ряд выбранного прогона читается по
  требованию, а не прореживается до обзорных точек.
- Запустить/остановить запись, перемотать ползунком, кнопками ±10 с или
  нажатием на график. Скорость проигрывания 0,25–10×. Пробел — пауза,
  стрелки — шаг на 1 с. Окно графика: 20 с, 60 с, 3 мин либо весь прогон.
- Вращать 3D-камеру перетаскиванием и менять масштаб колёсиком. Условные
  восемь колёс анимируются **двумя** измерениями скорости тележек. Красная
  тележка означает диагностическое расхождение; серая — отсутствие свежего
  сигнала. 3D-геометрия, эффективный радиус и пантограф условные.
- Видеть скорость передней/задней тележки, ручку, оба GNSS-канала, возраст
  измерений, расхождение, оценку скорости/пути C++, модельное ускорение,
  веса тележек и флаги проскальзывания/режима «только модель». На графике
  оценка выделена жёлтым; её интервалы отказа датчиков добавляются в закладки.
  Для `30618` по умолчанию подключается установленная train-only таблица тяги,
  как в ROS-ноде; для `30639` остаётся аналитическая модель.
  Карту можно приближать и перетаскивать. На ней отдельно показаны **сырые**
  позиции master/rover и жёлтая проекция оценённого `base_link` по обучающей
  карте пути. Скачки GNSS и разнесение антенн сохраняются.
- Нажать на закладку события и перейти непосредственно перед ним. Время в
  адресной строке (`?bag=...&t=...`) можно сохранить как ссылку на момент.

## Что отображается и что пока не моделируется

Все каналы идут по `header.stamp` относительно первого сообщения трёх
входных топиков. В каждом моменте UI использует только уже датированные
отсчёты: колёса считаются устаревшими через 0,3 с, команда через 0,5 с.
На графике длинный пропуск разрывает линию. Данные колёс переведены из
фактических км/ч в м/с (`/3.6`).

Показанные крупно скорость и путь берутся из **того же C++-ядра**, что
использует ROS-нода. API `/api/estimate/<bag>` передаёт в CLI только три
допустимых входных топика в порядке `messages.timestamp`. Выход
строится на сообщениях ручки контроллера; GUI сортирует уже готовый выход
по `header.stamp` только для показа. «Сырые колёса» рядом — простое среднее
свежих колесных скоростей для сравнения. GNSS на экране используется
**только для визуальной проверки** и никогда не подаётся в C++-оцениватель.

Красная подсветка в нижней визуальной диагностике при согласии master/rover
указывает, какая тележка отличается от них. Без согласованных GNSS оба
колёсных канала при расхождении помечаются как подозрительные: определить виновный по двум
скалярам невозможно. Автоматические закладки основаны на порогах; отдельно
помечены ручные проверенные эпизоды. Дефект GNSS не должен называться
буксованием колёс.

Схематический 3D-вагон остаётся на локальном прямом участке рельсов. Жёлтая
линия скорости и флаги получены из модели привода/динамики. На 2D-карте
жёлтый маркер отдельно показывает проекцию **base_link**: та же train-only
полилиния, три стартовых fix master, ближайший сегмент, направление по
конечной, затухание стартового смещения на 100 м и жёсткий перенос от
master на +9,873 м вдоль касательной и −3 м по высоте. Затем координата
переводится из ENU карты в ENU просмотрщика через ECEF. Дальнейшие GNSS-fix
в положении маркера не участвуют. При отсутствующей привязке или
неоднозначном старте маркер скрыт; остаётся относительная дистанция.
Это **визуальная проекция C++-дистанции**, а не побайтный replay
`/result/position` ROS-ноды: CLI выдаёт состояния на командах, тогда как
ROS публикует и по колёсным сообщениям. Для оценки жюри ROS-нода отдельно
переводит ENU в фиксированный числовой MGRS `37UCB`.
Сортировка входов по `header.stamp` применяется только к старому обзорному
слою: в новом C++ replay порядок приёма сохранён. CLI выдаёт состояние на
сообщениях ручки, а ROS-нода публикует также на сообщениях колёс, поэтому
частоты отображения могут различаться.

## Устройство

- `serve_simulator.py` — локальный HTTP-сервер и API:
  `/api/catalog` возвращает список bag; `/api/bag/<id>` — полный ряд пяти
  скоростных/командных потоков, обе ENU-траектории и диагностические события.
  `/api/estimate/<id>` — C++ replay трёх входных топиков, скорость,
  путь, ускорение, веса и флаги. После C++ replay сервер использует только
  три стартовых master fix для визуальной проекции base_link; их и последующие
  GNSS-данные он никогда не передаёт оценивателю. Оба ответа сжимаются gzip; в каждом кеше
  держится не более двух сжатых прогонов.
- `index.html`, `style.css`, `app.js` — проигрыватель, графики и карта.
- `scene.js` — автономная WebGL-сцена без внешних библиотек. При отсутствии
  WebGL интерфейс остаётся доступным без 3D.

В проверенном прогоне `30618_33bec73f` API отдаёт 11 579 передних, 11 562
задних, 23 602 команды; холодное чтение занимает около 1,7 с, gzip-ответ
около 677 КБ. Прогон без GNSS и длительный пропуск задней тележки также
проверены в браузере.
