# Как проверять результат без самообмана

## Три разных источника точности

1. **Train/validation GNSS-прокси.** Старый датасет: 122 директории bag, 97 уникальных записей после SHA-256 дедупликации; 42 train, 13 validation, 42 исторических holdout. Validation содержит только 30618 и одну сессию. Масштабы колёс, таблица привода и горизонтальная карта получены из train. Новый коэффициент доверия согласным колёсам выбран на train, зафиксирован и проверен на validation.
2. **Новый открытый объединённый эталон.** `30618_88aea4d9` из `check-code-with-bag.zip` содержит `/localization/kinematic_state`. Это отдельный диагностический набор. Его просмотр использован для выявления ошибок геометрии/контракта; после этого его нельзя называть скрытым независимым тестом. Ошибка скорости относительно него отличается от ошибки относительно сырых GNSS.
3. **Фактический ROS checker.** Официальный `hackathon_solution_checker.metrics` использует две очереди `ApproximateTimeSynchronizer`, по 100 сообщений, допуск 0,05 с. Итоговые результаты берутся после SIGINT и финального отчёта. Статистика ближайших меток офлайн не эквивалентна этому алгоритму.

Исторический holdout уже использовался сокомандником при выборе режима таблицы по трамваю. Его повторная оценка полезна для регрессий, но не восстанавливает независимость выборки. Не оценивать статистическую значимость по миллионам зависимых отсчётов как по независимым испытаниям.

## Разделение алгоритма и оценки

`reference_benchmark.py` декодирует эталон и разрешённые входы отдельно. C++ получает только `C/F/R/MF/RF/MV/RV`; другой код канала отвергается. MV/RV сейчас не используются. Оцениватель скорости получает контроллер и колёса; GNSS fix изменяет только маршрутную привязку. Нода не подписывается на эталон. Перед ROS-прогоном supervisor проверяет это через граф подписок и проверяет отсутствие других издателей `/result/*`.

Эталонная скорость — подписанное `twist.twist.linear.x`; ошибка положения — три компоненты и евклидова норма XYZ в численной системе организаторов, без подгонки поворота, масштаба, смещения или времени. Baseline и кандидат сравниваются на одинаковом пересечении временных меток. Отдельно сохраняются число результатов, число пар, coverage, пропуски, нечисловые выходы, максимальная и конечная ошибка. Отсутствующие выходы не считаются нулевой ошибкой.

## Воспроизведение

Для полного Python-набора установить `python3 -m pip install -r evaluation/requirements.txt` (NumPy/SciPy). Декодер, reference evaluator и сравнение ROS-выходов используют стандартную библиотеку; зависимости нужны для GNSS stress-прокси. C++ нода и её тесты этих библиотек не требуют.

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j2
ctest --test-dir build --output-on-failure
python3 -m unittest discover -s evaluation/tests -v

python3 evaluation/run_reference_ablation.py \
  --bag /absolute/path/to/30618_88aea4d9 \
  --outdir evaluation/runs/reference_ablation

# Выполнить в ROS Humble после сборки решения и установки официального checker.
bash tools/ros_reference_check.sh \
  --bag /absolute/path/to/30618_88aea4d9 \
  --outdir evaluation/runs/reference_ros \
  --config ros2_ws/src/tram_odometry/config/default.yaml \
  --ros-ws ros2_ws --rate 1 --timeout 1800
```

Каждый `outdir` должен быть новым. Полные записи и CSV лежат в игнорируемом `evaluation/runs`; компактные подтверждающие отчёты — в `evaluation/results`. В отчётах есть SHA-256 данных, бинарного файла, assets, конфигурации и исходников проверяющего кода. Для абляций также сохраняется точная команда каждого C++ replay.

Фактические ROS CSV сравниваются на одинаковом пересечении меток отдельной командой:

```bash
python3 evaluation/compare_reference_runs.py \
  --bag /absolute/path/to/30618_88aea4d9 \
  --before evaluation/runs/ros_original_1x/candidate.csv \
  --after evaluation/runs/ros_final_1x/candidate.csv \
  --out evaluation/runs/ros_common_mask.json
```

Velocity и position сопоставляются раздельно; для повторного сообщения канала на одной метке сохраняется последнее по receive-time. В отчёте есть число исключённых меток и SHA-256 общей маски. Это дополнительное сопоставление, не замена официального ATS.

Скорость старого и нового фильтра и потери обоих колёс воспроизводятся командами из [HEALTHY_WHEEL_GAIN_2026-09-27.md](HEALTHY_WHEEL_GAIN_2026-09-27.md). Протокол искусственно редких, задержанных и зависших GNSS описан в `evaluation/results/navigation_gnss_stress.json`; его paired-GNSS позиционный прокси не выдаётся за объединённый эталон.

## Что измеряет производительность

Финальный контейнер ограничивается `--cpus 2 --memory 512m`, проигрывание идёт 1×. `/proc` даёт CPU/RSS именно дочернего процесса `odometry_node`, а не всей связки checker/recorder. 100% CPU означает одно логическое ядро. VmHWM — максимум резидентной памяти процесса.

Независимый supervisor измеряет монотонное время приёма входного сообщения C/F/R и результата с той же `header.stamp`. Сохраняются p50/p95/max, охват и число перестановок callback. Разные DDS-подписчики могут получать сообщения в другом порядке; такие пары не становятся отрицательными задержками. Это наблюдаемая задержка доставки в стенде, не время от аппаратного датчика. `callback_to_position_publish_ms` ноды измеряет более узкий участок и показывается отдельно. Ускоренные прогоны используются для smoke, а не для заявления о задержке в реальном времени.

## Дополнительные проверки второго раунда

`speed_candidate_study.py` сохраняет результаты по bag и целым сессиям,
одинаковые контрольные метки и 1/3/5-секундные горизонты удаления обеих тележек.
Агрессивные варианты nominal-прогноза и быстрый bias отклонены после регрессий;
принят остаток ускорения только для потери пары. Публичный эталон и уже
просмотренный holdout остаются диагностикой, не независимым подтверждением.

`wheel_fault_benchmark.py` задаёт движение аналитически, отдельно от физической
модели алгоритма: стоянка/разгон/равномерное движение/торможение, скачки,
заморозка, плавная общая ошибка, задержки и пропуски. Для пары версий одинаковы
исходные байты, seed, шум, точные метки результатов и конечная маска. Coverage
считается относительно всех ожидаемых результатов. Частота колёс в этом
benchmark 10 Гц; отдельные C++ regression-тесты проверяют 10–100 Гц,
короткий интервал начала сбоя и пакетную доставку. Синтетический средний RMSE
не является официальной метрикой устойчивости или оценкой частоты отказов.

`navigation_gnss_stress.py` требует CSV с `frame_id,mapped,anchored`.
Абсолютный MGRS-прокси считается только в `mgrs_37UCB`; относительные `odom`
не смешиваются с ним, а уменьшают coverage. Нулевая абсолютная выборка даёт
`null`, а не нулевую ошибку. Все исключения кадров отражены в JSON.
Два train bag находятся более чем в 500 м от поставленной карты: их
относительный fallback не выдаётся за огромную абсолютную ошибку или успех.

Геометрическая поправка 6,098 м выведена из размеров трамвая до её оценки.
`body_heading_study.py` измеряет только перенос master→base_link на статической
карте с офлайн paired-GNSS, а не полную одометрию. Аналитический круговой
C++ тест независимо задаёт кузов и положения антенн. Проверка настоящего
Navigation по train/validation и ROS остаётся обязательной; локальная геометрия
не гарантирует улучшение интегрального пути на каждом рейсе.
