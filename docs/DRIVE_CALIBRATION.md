# Калибровка нелинейной тяговой модели

## Данные и статус результата

`evaluation/drive_calibration_train.json` содержит эмпирическую зависимость
ускорения от позиции контроллера и скорости. Скрипт
`evaluation/calibrate_drive.py` использует **только** bag набора `train` из
`tools/split_manifest.json`: 30 прогонов с GNSS для трамвая 30618 и 8 для
30639. Ещё четыре обучающих bag без нужных GNSS-измерений не участвуют в
идентификации. Для каждого значения контроллера от −15 до +15 есть шесть
скоростных интервалов 1–2, 2–3, 3–5, 5–8, 8–12 и 12–20 м/с.

Это **наблюдаемое продольное ускорение**, а не непосредственно измеренный
крутящий момент. Оно объединяет силу привода, загрузку, сопротивление,
уклон, поведение системы управления и незарегистрированные воздействия.
Поэтому физические параметры нельзя считать уникально идентифицированными
по трём доступным бортовым сигналам.

## Отбор и оценка неопределённости

- GNSS master и rover по скорости должны различаться менее чем на 0,3 м/с;
  передняя и задняя тележки — менее чем на 0,25 м/с; среднее колёс и master
  — менее чем на 0,5 м/с. Так калибровка не превращает буксование в силу
  привода.
- Позиция контроллера должна удерживаться не менее 1 с. Ускорение получено
  из GNSS-скорости центрированным фильтром Савицкого — Голея (~1,1 с).
  **Будущие точки используются только офлайн при обучении**, в ROS-ноду
  этот фильтр не включается.
- Центр каждой клетки — взвешенная медиана медианных ускорений отдельных bag;
  вклад одного bag ограничен весом 100 отсчётов. JSON хранит число отсчётов
  и bag, робастное отклонение между bag и стандартное отклонение отсчётов.
  Клетка пригодна для интерполяции, если есть ≥80 отсчётов из ≥3 bag.
  Это 92 клетки для 30618 и 49 для 30639. Малое отклонение между bag в
  отдельной клетке не гарантирует точности вне записанного маршрута;
  неопределённость прогноза не следует задавать ниже ~0,2 м/с².

## Что видно в данных

У 30618 после 1 с удержания в диапазоне 3–5 м/с типичные ускорения:

| Позиция | Медиана по обучающим bag, м/с² | Опора |
| ---: | ---: | --- |
| −8 | −0,05 | 1540 отсчётов, 18 bag |
| −7 | −0,75 | 646 отсчётов, 26 bag |
| −5 | −0,67 | 1537 отсчётов, 30 bag |
| 0 | −0,01 | 3452 отсчёта, 30 bag |
| +1 | +0,03 | 2706 отсчётов, 30 bag |
| +8 | +0,99 | 278 отсчётов, 17 bag |
| +9 | +0,97 | 740 отсчётов, 29 bag |

Позиция −8 на скоростях 3–8 м/с часто похожа на слабое замедление, хотя
соседняя −7 стабильно даёт около −0,75…−0,82 м/с². Это сильный признак
нелинейной или режимной логики управления; монотонная степенная формула по
номеру позиции не описывает её. У 30639 виден тот же эффект для −8 на
3–8 м/с, но обучающих прогонов существенно меньше.

Позиция −15 особенно неоднозначна. У 30618 в 1–2 м/с есть 178 отсчётов из
трёх bag с медианой около −0,03 м/с², а в 3–8 м/с лишь 69 отсчётов из
четырёх bag дают около −1,7 м/с². У 30639 движущихся примеров −15 ещё
меньше. Имеются и эпизоды ускорения при непрерывной −15 и согласии обоих
GNSS и колёс. Эту позицию нельзя считать известной тормозной силой; при
расхождении колёс увеличивать ковариацию и ограничивать срок прогноза.

## Как использовать в онлайн-модели

Для C++ упакован компактный train-only
`ros2_ws/src/tram_odometry/assets/drive_accel_table.csv`:

```csv
vehicle,notch,speed_bin,accel,uncertainty,count
30618,-8,3-5,-0.05228,0.35000,1540
```

Файл содержит только 141 достаточно поддержанную клетку (92 для 30618,
49 для 30639). `accel` — м/с², `uncertainty` — консервативная модельная
неопределённость в м/с² с нижней границей 0,2. Для −8 она не ниже 0,35,
для −15 не ниже 0,75. `count` — число обучающих отсчётов.

**Простое правило интерполяции для C++:** найти строку с точными `vehicle_id`,
целой позицией и скоростным интервалом, содержащим `v`. Внутри интервала
можно линейно интерполировать к центру соседнего интервала, только если его
строка тоже есть и интервалы соприкасаются. Через отсутствующий интервал
интерполировать нельзя. При `v<1` или `v≥20` м/с, неизвестном трамвае,
отсутствующей строке или разреженной позиции использовать физическую модель.
Для уверенности используется ограниченный вес
`λ = clip((0,75−uncertainty)/0,55, 0, 1) · (1−exp(−dwell/0,5 с))`.
Поправка `a = a_physics(q,v) + λ·[a_table(n,v)−a_physics(n/15,v)]`
вычисляется на каждом шаге прогноза при включённом флаге, затем измерения
колёс корректируют скорость обычным фильтром. Для −15 `λ=0`; для −8
максимум около 0,73. При отсутствии поддержанной клетки остаётся физическая
модель. Такой режим проверен точным C++ replay на validation.

Текущая C++ grey-box модель содержит нелинейное насыщение силы моментом и
мощностью, разные постоянные времени тяги/торможения и сопротивление. Она
остаётся запасной физической моделью. ROS-нода включает табличный остаток
по умолчанию только для `30618`. Для `30639` по умолчанию действует
физическая модель: для его таблицы нет независимой validation-сессии, а
проверка holdout показала небольшое ухудшение. Параметр
`enable_drive_table` позволяет переопределить выбор, а
`drive_table_path` — указать другой CSV.

Интерпретировать таблицу как точную истинную силу нельзя: уклоны/масса и
режим фактического тормозного оборудования скрыты. Начальное значение
скорости при длительном пропуске двух колёс также должно приходить из
последней доверенной оценки, а не из GNSS во время работы.

## Стресс-тест обеих тележек

Первоначальный Python-тест моделировал одновременный обрыв обоих колёс на
1, 3 и 5 с в 284
эпизодах 12 **валидационных** bag 30618. Начало выбирается на сетке 30 с;
вокруг него обе GNSS-скорости и колёса согласованы. Скорость старта берётся
от колёс, а после обрыва модель получает лишь поступающие позиции
контроллера. GNSS служит только эталоном после расчёта. Это отдельно
проверяет пригодность модели при потере одометрии, без вмешательства в
конкурсную ROS-ноду.

| Потеря колёс | Удержать последнюю скорость, RMSE м/с | C++ формула без адаптации, прибл. RMSE м/с | Таблица train, RMSE м/с | RMSE дистанции: удержание / формула / таблица, м |
| ---: | ---: | ---: | ---: | --- |
| 1 с | 0,517 | 0,209 | 0,196 | 0,259 / 0,110 / 0,105 |
| 3 с | 1,479 | 0,550 | 0,476 | 2,255 / 0,865 / 0,755 |
| 5 с | 2,258 | 0,800 | 0,657 | 5,928 / 2,194 / 1,837 |

На пятисекундном горизонте таблица лучше физической формулы на 11 из 12
валидационных bag. Бутстрэп с единицей ресэмплинга **bag** даёт для снижения
RMSE скорости примерно 0,143 м/с (95% интервал 0,077–0,222 м/с). Точки
внутри одного bag нельзя считать независимыми испытаниями.

Этот предварительный тест воспроизводит уравнение с лагом привода на Python,
без полного C++ состояния оценивателя. После него проведён точный
парный replay **того же C++ Estimator**, который использует ROS-нода.
На 284 чистых неперекрывающихся окнах из 12 validation-bag оба колёсных
канала скрывались на 5,12 с. В модель поступали только уже полученные
позиции контроллера; GNSS использовался после расчёта как эталон.

| Горизонт | Скорость RMSE, физика → таблица, м/с | Дистанция RMSE, физика → таблица, м |
| ---: | ---: | ---: |
| 1 с | 0,19444 → 0,17502 | 0,10948 → 0,09992 |
| 3 с | 0,48051 → 0,41377 | 0,77906 → 0,68163 |
| 5 с | 0,67174 → 0,55471 | 1,91471 → 1,61997 |

На непрерывном validation replay 30618 таблица также улучшила скорость
`0,0359→0,0345 м/с` и медиану модуля конечного дрейфа на 12 длинных bag
`0,226→0,188%`. На holdout 30618 улучшение составило
`0,1251→0,1241 м/с` и `0,254→0,227%` по девяти длинным bag. Для 30639
отдельная таблица ухудшила holdout скорость `0,1145→0,1155 м/с` и дрейф
`0,995→1,032%`; поэтому она по умолчанию отключена. Holdout участвовал в
**выборе режима** `30618 on / 30639 off`, так что после этого решения его
нельзя считать полностью нетронутым контрольным набором. Параметры
таблицы и масштабы колёс по holdout не подбирались. Для 30639 по-прежнему
нет независимого validation-прогона, а синтетический обрыв не доказывает
устойчивость к общему плавному скольжению всех осей.

Воспроизведение предварительной калибровки:
`py -3.12 evaluation/calibrate_drive.py` из корня проекта. Точный C++
стресс-тест: сначала собрать `evaluation/replay_cli.cpp` вместе с
`src/estimator.cpp`, затем выполнить
`py -3.12 evaluation/table_blackout_ablation.py --exe <путь-к-replay_cli>`.
Результат записывается в `evaluation/table_blackout_validation.json`.
Нужны NumPy/SciPy, `analysis/signals/notch_speed_dwell_summary.csv` и
распакованные bag. Скрипт стресс-теста не читает holdout.
